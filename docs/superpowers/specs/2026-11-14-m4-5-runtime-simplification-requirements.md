# M4.5 – Luna-Driven Runtime Simplification

## Мета

Спростити когнітивну архітектуру `softsock/liac-ai`.

**Luna – єдиний керівник поведінки, контексту та автономних намірів Liac. Nemotron – модель, що генерує мовлення. Runtime – мінімальна інфраструктура для асинхронності, збереження стану, KV-cache optimization і streaming.**

Зараз система частково реалізує іншу архітектуру: Luna генерує типізовані пропозиції, які Runtime перевіряє та схвалює.

Потрібно усунути цей зайвий рівень контролю, зберігши все корисне з M0–M4.4.

Це цільовий рефакторинг, а не нова підсистема.

## 1. Спочатку досліди поточний код

Використай актуальний HEAD `codex/m4-4-conversation-lab` як основу.

Прочитай релевантні розділи `PROJECT_BLUEPRINT.md`, `AGENTS.md`, документацію M0, M1.5, M2, M4.2, M4.3, M4.4 та реалізації:

- `minds/luna.py`, `minds/deep.md`, `minds/character.md`
- `runtime/deep.py`, `runtime/journal.py`, `runtime/orchestrator.py`
- `contracts/deep.py`, `contracts/state.py`
- `context.py`, `app.py`
- Поточні механізми trace та Conversation Lab

Знайди всі місця, де Runtime не просто виконує технічні операції, а визначає, чи дозволено застосувати рішення Luna.

Не видаляй код автоматично. Спочатку визнач, яка логіка справді потрібна для збереження стану, конкурентності та KV cache, а яка існує виключно через стару модель `proposal → validation → decision`.

Не додавай нових abstraction layers.

## 2. Онови архітектурний контракт

Перед реалізацією виправ `PROJECT_BLUEPRINT.md`.

Зокрема переглянь D-06, D-07, I-05, розділ Ownership and Model Roles та Luna → Fast Update Protocol.

Нове правило:

**Luna owns cognition. Runtime owns execution.**

Luna самостійно вирішує:

- Що запам'ятати, забути або переосмислити.
- Як змінити Markdown Context.
- Які інтереси, наміри та особисті особливості підтримувати.
- Чи проявляти автономну ініціативу.
- Коли запропонувати власну репліку.
- Який контекст залишити після compaction.

Runtime не повинен оцінювати зміст цих рішень.

Fast не повинен чекати Luna та не повинен мати окремої когнітивної логіки, яка конкурує з нею.

## 3. Спрости Luna → Markdown

Основна функція Luna – асинхронно спостерігати за розмовою та редагувати один вільний Markdown-документ.

Збережи існуючий `context_note` у SQLite та `context.md` як файлову проєкцію, якщо це дозволяє уникнути міграцій.

Поведінка:

- Luna отримує нові події, попередній Markdown та необхідний історичний контекст.
- Luna повертає новий Markdown або `null`, якщо нічого змінювати не потрібно.
- Новий Markdown атомарно стає поточним станом.
- Наступний Fast request використовує актуальну версію.
- Поточна Fast-генерація продовжується з незмінним snapshot.

Прибрати для Markdown updates:

- Обов'язкові `source_event_ids`.
- Семантичні dependency checks.
- Складні `NoteProposal` та `DeepDecision`, якщо вони більше не потрібні.
- Валідацію того, чи виправдане оновлення змістом подій.
- Зайві proposal fingerprints та audit operations, які існують тільки для схвалення рішення Luna.

Не потрібно змушувати Luna повертати громіздкі JSON-об'єкти.

Можна залишити мінімальний структурований envelope для розрізнення `no change`, `replace context` та команд ініціативи. Обери найпростіший варіант, сумісний із поточним OMP transport.

Не створюй спеціальний Markdown parser, систему секцій, психологічні метрики чи правила характеру.

## 4. KV-cache optimization – незмінний пріоритет

Це найважливіша технічна вимога.

Збережи перевірений порядок Fast prompt:

1. Стабільна Character Identity.
2. Незмінний Context Epoch.
3. Exact conversation history.
4. Luna-managed Markdown Context.
5. Поточний input.

Markdown має залишатися в змінному хвості prompt.

Зміна лише Markdown не повинна змінювати байти стабільного префікса.

Не додавати в prompt перед Markdown випадкові IDs, revision numbers, timestamps або інші динамічні metadata.

Не змінюй перевірений Nemotron renderer, tokenizer, streaming transport і механізм frozen snapshots без необхідності.

**Fast ніколи не чекає завершення Luna inference.**

## 5. Context Epoch та compaction

Не видаляй Context Epochs: вони потрібні для керування обмеженим context window.

Але розділи дві відповідальності.

**Runtime:**
- Визначає фактичний token budget.
- Відстежує заповнення контексту.
- Технічно виконує epoch transition.
- Зберігає канонічну історію в Journal.

**Luna:**
- Визначає, які факти, події, спогади й наміри важливі.
- Формує зміст компактного контексту.
- Вирішує, що залишити, а що прибрати.

Runtime не повинен використовувати власні евристики важливості як альтернативного когнітивного керівника.

Якщо Luna тимчасово недоступна, система може використати лише мінімальний технічний механізм забезпечення контекстного ліміту. Він не повинен видавати механічно відібрані фрагменти за семантично правильну пам'ять Luna.

Не змінюй сам механізм KV cache, якщо можна обмежитися спрощенням формування Epoch.

## 6. Спрости автономну ініціативу

Поточний M4.3 містить надто багато політики Runtime.

Прибери залежність від:

- Обов'язкових `source_event_ids`.
- Правила однієї спроби на останнє повідомлення користувача.
- Семантичної прив'язки ініціативи до поточного user turn.
- Автоматичного скасування наміру лише через зміну Markdown revision.
- Жорсткої політики cooldown / TTL / eligibility, нав'язаної Runtime.

Luna визначає, чи потрібна репліка, її задум і момент виконання.

Підтримай мінімальні дії:

- Нічого не робити.
- Запланувати автономну репліку.
- Скасувати власний очікуваний намір.

Runtime просто запускає Nemotron з відповідним intent, використовуючи наявний Fast pipeline.

Збережи тільки технічні правила:

- Один активний Fast stream.
- Нове повідомлення користувача має пріоритет над поточним автономним мовленням.
- Cancellation закриває stream.
- Shutdown не залишає працюючих задач.
- Restart не відтворює випадково старе автономне мовлення.

Не створюй нового scheduler framework, Attention Engine, Behavior Evaluator або Intent Manager.

## 7. Поведінка Nemotron

Переглянь `character.md`.

Наразі Luna working context описаний як набір необов'язкових ідей, які Fast може ігнорувати.

Нова відповідальність:

- Luna визначає актуальну поведінкову перспективу персонажа.
- Nemotron реалізує її природним мовленням.
- Nemotron самостійно формулює речення, жарти й реакції, але не виступає окремим керівником характеру.
- Persona не повинна перетворюватися на assistant behavior.

Залиш коротку стабільну базову інструкцію, необхідну для ідентичності Liac.

Не додавай фіксованих personality sliders, жорстких шаблонів відповідей чи антишаблонних перевірок у Runtime.

## 8. Збережи Conversation Lab

M4.4 залишити працездатним.

Інтерфейс має продовжувати показувати:

- Усі доступні Fast і Luna calls.
- Повні доступні prompts та responses.
- Актуальний і попередні Markdown contexts.
- Epoch transitions.
- Заплановані та виконані ініціативи.
- Streaming, cancellation, errors та timing.
- Історичні зв'язки між репліками й процесами.

Прибрати із UI стару термінологію «схвалення» рішень Luna там, де Runtime більше нічого не схвалює.

Відрізняй:

- Luna змінила контекст.
- Luna залишила контекст без змін.
- Сталася технічна помилка виконання.

Не втрачати compatibility зі старими M4.4 traces, якщо достатньо простого read-only fallback.

Не створюй нову систему трасування чи окремий debugger.

## 9. Технічні межі

Дозволені мінімальні перевірки типів, можливості прочитати відповідь, обмежень inference context та коректності атомарного запису.

Це не перевірки правильності мислення Luna.

Не потрібні:
- Behavioral validators.
- Evidence verification для думок і намірів Luna.
- Автоматичні оцінювачі природності.
- Великі нові тестові набори.
- Додаткові agent layers.
- Нові бази даних або фреймворки.
- Перебудова всієї системи під нову архітектуру.

Використовуй існуючий Journal і наявну послідовну Deep worker execution. Не вводь нову складну concurrency-модель.

Не змінюй механізм безпечної технічної ізоляції OMP та не надавай моделі довільного доступу до файлової системи чи shell. Luna керує контекстом через призначений для цього шлях запису.

## 10. Порядок реалізації

1. Проаналізуй код і склади коротку карту того, що залишається, що спрощується та що видаляється.
2. Онови Blueprint відповідно до реальної цільової архітектури.
3. Спрости Luna result protocol та застосування Markdown.
4. Прибери зайві behavioral guards з initiative.
5. Узгодь `character.md` / `deep.md` із новими ролями.
6. Адаптуй Conversation Lab до спрощеного Runtime.
7. Перевір базовий запуск, streaming, контекстне оновлення, cancellation та відсутність очевидної регресії KV-cache prefix.

Не проводь багатогодинних тестів або повної симуляції як частини цього рефакторингу. Не додавай evaluation framework.

Існуючі тести можна адаптувати там, де вони фіксують стару, навмисно видалену поведінку. Не витрачай час на збереження застарілих контрактів заради зелених тестів.

- Як збережено KV-cache optimization.

Не роби push або PR.

Після перевірки створи один змістовний коміт.

## Definition of Done

Luna асинхронно спостерігає за діалогом, самостійно редагує Markdown та визначає автономні наміри.

Runtime не оцінює і не схвалює її поведінкові рішення.

Nemotron відповідає без очікування Luna, отримує frozen context snapshot і зберігає переваги KV cache.

SQLite Journal, Conversation Lab, cancellation і restart залишаються працездатними.

**Фінальна мета – не більше функцій. Фінальна мета – менше коду, менше умов і пряміший контроль Luna над Liac.**
